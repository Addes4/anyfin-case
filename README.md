**Run:** `uv run classify.py data/final.csv -o predictions.csv` (any CSV path works). `adrian-sohrabi.csv` holds the final-set predictions and `adrian-sohrabi-validation.csv` the validation-set predictions. The API key is read from `ANTHROPIC_API_KEY` or `.env`, and `MAX_USD` (default 5) and `DEADLINE_S` (default 480) cap spend and time. Exit code 1 means API failures or limits left rows unclassified; exit code 2 means the input was invalid. `uv run classify.py --eval` scores it leave-one-customer-out; `uv run test_classify.py` and `python3 test_synthetic.py` run the offline tests.
**Approach:** rules only where the structure proves the category: card-bill payments with their receipts on the card, own-account transfers that match uniquely and whose texts name only the customer's own accounts, salary, interest, cash withdrawals, collector bills, the provider's own invoices, and Swish with a clear message or none. Every purchase, including those through KLARNA*/QLIRO*/PAYPAL* and similar, goes to Claude Opus 5.5 at low effort. The model gets unique keys (text, money in/out, amount band, account type including inferred savings, and "monthly" for 3+ months with similar amounts) in batches of 60, uses the training rows as examples, and answers `unknown` when unsure. Only Swish names in the "FIRSTNAME X" form and words in bank transfers that are not the customer's own account names are redacted. Everything else is sent as is, including Swish counterparties in other formats, which may be full names.
**Measured:** leave-one-customer-out on training scores 100.0, including the 636 rows whose normalised text is unseen. Those are often a new branch of a known chain, so this is weak evidence for genuinely new merchants. Rules label 22% of training rows and 20% of validation rows. A cold validation run (1,183 rows, 339 unique model items) takes 11 s and costs ~$0.39; a warm re-run takes 1 s and costs $0. For 5,517 rows I estimate ~1 min and ~$1.80, which is not measured. Cold runs can differ slightly, since the model takes no sampling settings and the cache is not in git.
**Cost at 10M rows/month (API only):** ~$0.0012 per unique model item, about $0.00033 per row at this set's duplication. That is ~$3,300/month with no cache, up to ~$0.0012 per row if nothing repeats, and roughly 1/40 of that on Haiku 5.5. With the persistent cache, cost scales with new merchant keys (~$120 per 100k). I have not measured the new-key rate at that volume, and the system itself (an in-memory JSON cache, pairing within each customer) would need a database-backed cache and partitioning to run at that scale.
**Robustness:** on 876 synthetic stress rows across 32 scenarios, the rules make 0 wrong calls. The full pipeline scores 83.56 at 98.41% precision; all 12 disagreements are whether "Swish … tack" is a personal transfer or `unknown`. Repeated templates do not establish hidden-test accuracy; see [SYNTHETIC.md](SYNTHETIC.md). **With another day:** calibrate `unknown` against held-out customers instead of the model's own confidence, test more banks' formats, turn the cache into a reviewed merchant table, and send only ambiguous rows to Opus while Haiku labels the rest.
